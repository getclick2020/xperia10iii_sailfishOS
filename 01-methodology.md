# Методика измерений

## 1. Узлы power_supply

В системе: `battery`, `bms`, `battery_ext`, `main`, `usb`, `dc`, `pc_port`.

- **`battery`** — «причёсанный» узел для userspace.
- **`bms`** — сырой узел топливного датчика (QGauge). Богаче и точнее.

### Соглашения о знаке — РАЗНЫЕ у двух узлов
| Узел | Плюс означает |
|---|---|
| `battery/current_now` | **заряд** |
| `bms/current_now`, `bms/current_avg` | **разряд** |

Проверено: при подключённом кабеле `battery/current_now = +501404`,
`bms/current_now = −423584`. Путать нельзя.

### Разрешение счётчиков заряда — КРИТИЧНО
| Счётчик | Шаг | В мА·ч | Комментарий |
|---|---|---|---|
| `battery/capacity` | 1% | 40,49 | шумит на коротких окнах |
| `battery/charge_counter` | **1%** | **40,49** | НЕ 0,1%! |
| `bms/charge_counter` | 1% | 40,49 | то же значение |
| **`bms/cc_soc`** | **0,01%** | **0,4049** | основной инструмент |
| `bms/battery_raw_soc` | 0,01% | 0,4049 | сырой, дрейфует по напряжению |

Проверка кратности: все наблюдавшиеся `charge_counter` делились на 40490
без остатка (3441650 = 4049×850, 3401160 = 4049×840, 3158220 = 4049×780 и т.д.).

`cc_soc` и `charge_counter` согласуются: cc_soc 8409 ↔ charge_counter 3401160 (84,0%).

**Не использовать `battery_raw_soc`** для расчёта тока: сразу после отключения
кабеля напряжение релаксирует, и сырой SOC падает быстрее реального.

## 2. Формулы

Ток: I [мА] = Δзаряд [мА·ч] / Δвремя [ч]
Δзаряд из cc_soc = Δcc_soc × 0,4049 мА·ч (при FCC 4049 мА·ч)
Δзаряд из charge_counter = ΔµAh / 1000

Погрешность (квантование ±1 шаг): δI = шаг [мА·ч] / Δвремя [ч]

Примеры для cc_soc: 15 мин → ±1,6 мА; 20 мин → ±1,2 мА; 1,8 ч → ±0,23 мА.
Для charge_counter: 8 ч → ±5 мА; 58 ч → ±0,7 мА.

**Всегда читать `charge_full` заново**: у Sony есть обучение ёмкости
(`[SOMC CL]`), оно меняет FCC, и масштаб расчёта поедет.

## 3. Как определить, спал ли телефон

### Способ A — по idle из /proc/uptime
Второе поле — сумма idle по всем 8 ядрам. **Во время сна учёт idle не идёт.**

доля бодрствования ≈ Δidle / (8 × Δuptime)

- ~0,5% → телефон спал
- ~99% → телефон бодрствовал всё окно

Это самый быстрый и надёжный признак.

### Способ B — монотонные часы vs boottime
`uptime` идёт всегда (включая сон). Колонка `last_change` в
`/sys/kernel/debug/wakeup_sources` — это `ktime_get()`, **монотонные часы,
во сне не идут**. Максимум `last_change` ≈ текущее монотонное время.


Побочный эффект: цикл с sleep 1 сам НЕ будит систему (таймер не является
wakeup-источником), поэтому телефон спит свободно, а граница окна замечается
с небольшим перелётом. Перелёт не вредит — считать по фактическим меткам.
Определение «телефон бодрствует» по частоте итераций: если sleep 1
завершается за ~1 с реального времени — система awake.

**5. Отключение скрипта от сессии**
nohup ... & защищает от SIGHUP, но не от уборки scope сессии.
Надёжнее — transient-юнит systemd:

systemd-run --unit=mytest --collect /bin/sh /home/defaultuser/mytest.sh
systemctl is-active mytest

Пока кабель подключён, идут сообщения зарядника каждые ~13 с
(aicl-done, get_batt_id_ohm, cap_learning_update) и система не спит.

**7. regulator debugfs — семантика**
Каталог: /sys/kernel/debug/regulator/<имя-регулятора>/

| Файл | Права | Смысл |
| --- | --- | --- |
| use_count | r | число включённых ссылок потребителей |
| open_count | r | число получивших ссылку |
| enable | rw | чтение — regulator_is_enabled(), т.е. состояние железа |
| force_disable | rw | чтение — то же состояние; запись — regulator_force_disable() |
| voltage, mode | rw | если драйвер поддерживает |
| подкаталоги | — | имена потребителей |

force_disable игнорирует use_count и гасит выход даже при активных
потребителях. Именно так удалось обесточить панель, которую драйвер не отпускал.

**Две ловушки**
1. use_count не уменьшается при force_disable. Проверять успех по enable,
а не по use_count и не по regulator_summary (там остаётся use≥1 и
последнее запрошенное напряжение, а не измеренное).
2. Откат невозможен записью в enable: regulator_enable() подаёт питание
на железо только при переходе use_count 0→1. Счётчик уже ≥1 → железо
останется выключенным. Восстановление только перезагрузкой/выключением

**Порядок гашения цепочки AMOLED**
Обратный порядку включения: ibb → ab → bob → l6.
bob — вход для ab/ibb; гасить его первым нельзя.

**Риск для матрицы**
Если после force_disable что-то попытается включить дисплей, драйвер решит,
что питание подано (use_count≥1), и подаст сигналы DSI без AVDD/AVEE/VCI —
состояние вне спецификации. Поэтому перед такими тестами гасить экран,
не касаться телефона, включать режим полёта и завершать скрипт poweroff.

8. Статистика сна — где лежит
**| Путь | Что даёт |**
| --- | --- | --- |
| /sys/power/rpmh_stats/master_stats | сон по мастерам APSS/MPSS/ADSP/CDSP |
| /sys/kernel/debug/lpm_stats/ | резидентность по уровням, включая [L3] suspend |
| /sys/power/ddr/residency | уровни LPM памяти и частоты |
| /sys/power/system_sleep/stats legacy | RPM, на RPMh-цели нули — вероятно не заполняется |
| /sys/kernel/debug/wakeup_sources | кто будит и кто срывает suspend |

Тик RPMh = 19,2 МГц. Проверка: APSS accumulated / 19,2e6 ≈ uptime.
Пример: 0x4f9f81ed94b = 5 471 656 139 083 тиков / 19,2e6 = 284 982 с при
uptime 287 942 с → 98,97%.

**9. Чек-лист валидности замера**

Перед тем как доверять цифре:
1. Вмешательство применилось? enable=0, сервис inactive, процесса нет,
init.svc.*=stopped. Не верить команде без проверки.
2. Телефон спал? Доля бодрствования по idle; SS вырос.
3. Нет загрязнения? Кабель вынут до старта окна; нет циклов перезапуска
в журнале; нет спама execv; графика в одинаковом состоянии в обоих окнах.
4. Одна переменная за раз. Иначе разница не атрибутируется.
5. Окна и паузы по wall-clock, не по sleep.
6. charge_full записан в каждом снимке.
7. stderr не спрятан. 2>/dev/null уже дважды скрывал реальные ошибки. 
Для записи в sysfs правильно: ( echo X > /path ) 2>&1 — иначе stderr
уйдёт в тот же файл.
8. Разрешение счётчика соответствует окну. Для окон < 1 ч — только cc_soc.

**10.Known-good базовые условия для замера**
• Режим полёта включён, Wi-Fi и BT выключены
• Экран погашен кнопкой, телефон не трогать
• Кабель отключён
• HAL Bluetooth отключён, bluebinder замаскирован (постоянные изменения)
• Графическая сессия работает (её остановка блокирует сон — см. 08)
